# Multiplayer data: files, versions, copies, bringing items back

Owner: keepsafe. Code: `platform/include/port/mp_keepsafe.h`, `platform/src/mp/mp_keepsafe.cpp`. Tests: `tests/mp/keepsafe_build.sh` (keepsafe_test + keepsafe_cut_test), `tests/mp/config_lock_build.sh` (keepsafe_cfg_test), `tests/mp/keepsafe_mutations.py`. The calls the menus make: `share/keep/API.md`.

## 1. What is a player's multiplayer data

Folder `ux0:data/smg` on the Vita (`$PETARI_DATA_DIR` on the desktop; the account folder `online/` follows `SMG_ONLINE_DIR` / `SMG_DATA_DIR`).
The single-player saves, `<data>/saves`, are **not** multiplayer data: nothing in keepsafe (copies, bringing back) writes them (the tests hash the folder before and after every step). One thing besides the game's own save does write there: the atomic single-player save, which is on by default (next table row).

| File (below the data folder) | Writer | Reader | Format version rule |
|---|---|---|---|
| `mp/mp.cfg`, `.bak` | `mp_config.cpp` mp_config_save | mp_config_load | text, `version = 1`. Unknown keys: see 3 |
| `mp/flow.cfg`, `.bak` | `mp_ui_flow.cpp` | same | text, `version = 1` (`kFileVersion`; a newer file is never written). Keys: `char_picked`, `reach`, `last_coop`, `falls_asked`, then `played = <name>` (newest first, at most 20) each optionally followed by `played_code = <friend code>`; unknown lines are kept |
| `mp/coop.cfg`, `.bak` | same | same | text, `version = 1`; per Team File `file`, `galaxy`, `player = <look> <name>` lines (who played on it; not a save) |
| `mp/conntest.txt` | `mp_conntest_sys.cpp` | nobody (the report copies it) | output only, regenerated |
| `report.txt` (data folder) | `mp_report.cpp` | nobody | output only, a bug report to send; not part of the data set |
| `mp/saves/title/00010000/524d4750/data/GameData.bin` (+ `.mptmp`, `.mpbak`, `.mpbad`) | `MpSaveGame.cpp` via `mp_save_*` | same | binary, header version 2, checksum, see mp_savefile.h |
| `saves/title/00010000/524d4750/data/GameData.bin.mptmp`, `.mpbak`, `.mpbad` (data folder; **single-player** save) | `platform/src/nand/nand.cpp` (atomic writer, OFF by default for single player: Settings "Safe saves" or `SMG_ATOMIC_SAVES=1` turns it on; always on while a multiplayer session is active) through `mp_save_commit_tmp` | `port_nand_set_root` at boot (`mp_save_recover`) | `GameData.bin` is written as `.mptmp` (truncated, filled, `NANDClose` syncs it), validated as a GameData.bin, read back, the old file kept as `.mpbak`, the new one renamed in, read back. `.mptmp` exists only during a write or after a cut; `.mpbak` (about 48 KiB) stays. `.mpbad` is a damaged file kept aside and is never deleted. At boot, a **missing** `GameData.bin` with a `.mptmp` beside it is completed from it (a cut between the two renames; the `.mpbak` is used only if the `.mptmp` is torn). A missing file with only a `.mpbak` is left as it is and logged (a save deleted outside the game). `NANDDelete` removes `.mpbak` and `.mptmp` with the file (so a save deleted in the game stays deleted); an older game, or a hand deletion, does not. Costs on a dev machine: 4.5 to 6 ms a save against 1 to 2 ms; not measured on a Vita |
| `mp/backups/GameData-*.bin` | `mp_save_backup` | the write-back | copies of single-player files made before a write-back |
| `mp/recovery/session-NNNNNNNN.bin` (+ `discarded/`) | `mp_save_recovery_write` | MpSaveGame | binary `MPRC`, version 1, CRC |
| `online/online.dat`, `online_<hash>.dat` (+ `.mptmp`/`.mpbak` of the atomic writer, `.prev`, `.prev.1`, `.prev.2`) | `mp_service.cpp` SaveAccount through `mp_keepsafe_account_store` | LoadAccount | binary `SMGO`, version 1, CRC (112 bytes). **A credential.** One file per service address |
| `online/keepsafe-own.txt` | the account store (mp_keepsafe_account_store) | the account store | one 8-hex-digit line per credential (player id + token, fingerprinted) this console itself held: tells its own old credential (kept in `.prev`) from a foreign one (never kept). Atomic writer |
| `mp-keepsafe.stamp` (data folder) | keepsafe | keepsafe | text `keepsafe = 1`, own CRC; unknown lines kept (also an earlier design's `pending` / `declined` lines: never read) |
| `mp-backups/<version>-<date>-<n>/` (data folder) | keepsafe | keepsafe | the automatic copy at a version change, see 4 |
| `mp-backups/before-<date>-<n>.smgmp`, `copy-<date>-<n>.smgmp` | keepsafe | keepsafe | "Before bringing back" and "Make a Copy" files, see 5 |

The friends list is not stored (it is fetched from the service); there is no friends cache file.

## 2. Updating the game

Installing a new version of a Vita homebrew replaces the application folder (`ux0:app/...`), never `ux0:data`. The only risk is our own code at the first start of a new version, so:

1. **Copy first.** `mp_port_boot` calls `mp_keepsafe_boot(version, build)` before `mp_core_boot` (which writes mp.cfg). It reads the stamp; when the version or build differs it makes ONE new copy of the multiplayer data (section 4), verifies it by reading every file back, and only then writes the stamp. It never changes a live file. A normal start reads the stamp (about 100 bytes, into a 4 KiB buffer), makes at most two `stat` calls and writes nothing; single player pays exactly the same (test Boot: read and stat counts, the whole data folder byte-identical).
2. **If anything fails** (card full, folder not writable, a file that cannot be read, a folder that is there but cannot be listed) or the stamp cannot be READ (an I/O error: there, but the read fails): nothing is changed and no stamp is written, so the copy is tried again at the next start. Multiplayer starts anyway; `mp_keepsafe_may_migrate()` is false for that run and `mp_keepsafe_notice_take()` returns `MP_KS_NOTICE_NO_COPY` (in memory only; it comes at every such start), or `MP_KS_NOTICE_NO_SPACE` when the failure was a real out-of-space result (`ENOSPC`, or the free-space check): only that one may say the card is full. Tests: CopyFailures (card full: NO_SPACE; unreadable stamp; a name that already exists), StrayFiles (a folder that is a file: NO_COPY, not "full"), FailedListing (`opendir` of the Team File folder, `mp/` or `online/` fails: no copy, no stamp, notice, and the next start copies everything); keepsafe_cut_test version-copy (a cut at every call: after the restart a verified copy of the Team File exists).
   A stamp that is there, is read, and does not parse (a bad CRC, text that is not a stamp, an empty file) counts as NO stamp: the copy is made as from `none`, then a good stamp is written by the atomic writer (test StampParse; the stamp as a directory is a read error, not this).
3. A newer game's stamp (`keepsafe = 2`) is never rewritten. An older game that finds it copies the data unless a verified copy of exactly that data (every file name, size and fingerprint) exists; it migrates nothing (`may_migrate` false) (test NewerStamp).
4. **Stale files of the earlier design** on a tester's card (`mp-keepsafe.journal`, `.kstmp` / `.ksold` files, `pending` / `declined` stamp lines, `undo-*` folders) are left alone: never read, never removed, never copied (test OldDesign).

## 3. Version policy for every multiplayer file

- **Newer than me** (a higher `version`, a header version this code does not know): the file is left byte for byte as it is. `bring_back_slot` returns `MP_KS_NEWER` and writes nothing if this console's Team File is a newer game's (BringBackSlot); `use_account` and the account store never write over a newer game's account file (Account); settings are never brought back over a newer mp.cfg / flow.cfg / coop.cfg (Settings).
- **Older than me**: read as it is (missing keys take their defaults). Before the first write in a new version the old file is in the copy made at that start, so a bug in migration cannot lose it.
- **Unknown keys** of mp.cfg: mp_config.cpp keeps them on save, up to 48 keys (keys under 32, values under 160 characters); beyond that they are dropped (tests/mp/keepsafe_findings.sh K3 checks one key). flow.cfg / coop.cfg: `version = N` like the others; a newer file is never written, and the loaders read the `.bak` when the file is missing.
- **Damaged** files: keepsafe never writes over a file it cannot read (a read error other than "missing" stops the call: `MP_KS_IO`; for the account store this holds for every `.prev*` file and the own list too, and the call changes nothing: AccountReads; a Team File that fails the file's own checks: `MP_KS_BAD_FILE`) and never deletes anything it cannot parse (PruneAndPins, BlocksAndDamage). An mp.cfg that is there but does not parse (the game then runs read-only) CAN be replaced from a copy, because that is what a restore is for (ConfigRestore); one written by a newer game never. What the settings and save code do with a damaged file of their own is theirs (keepsafe_findings.sh K1, K2; the save layer's tests).
- Text files carry `version = N` on their own line; no such line is version 1. New files of this module: the stamp (`keepsafe = 1`), the folder copy's manifest (fmt 2), the copy file (format 1).

## 4. Copies

**The rule.** Every change to LIVE data is ONE file replaced by that file's own writer: the save layer's `mp_save_write_atomic` for the Team File and the account files (recovery at start: `mp_save_recover*`), `mp_config` / `mp_ui_flow`'s writers for the settings. Nothing in keepsafe renames, removes or truncates a live file otherwise; it does not even repair one (test ReadOnlyCalls: a Team File whose write was cut is only read). Copies are NEW files in `<data>/mp-backups/`:

| Name | Made by | Holds |
|---|---|---|
| folder `<version>-<YYYYMMDD>-<n>/` | `mp_keepsafe_boot` at a version change | the multiplayer data of this console: `mp/` without `mp/backups` (the single-player safety copies) and without `mp/recovery` (the recovery checkpoints are in no copy), and `online/online*` (with `.prev*`); no writer temporaries (`*.tmp`). Only files whose NAMES the game's own writers use: `mp.cfg`, `flow.cfg`, `coop.cfg`, `conntest.txt`, `report.txt`, `GameData.bin` (each with the writers' `.bak` / `.mpbak` / `.mptmp` / `.mpbad*`), and `online.dat` / `online_<8 hex>.dat` (also with `.prev`, `.prev.1`, `.prev.2`). Any other file (a stray, a hand-edited `mp.cfg.unreadable`, any size) is skipped and the log says which (StrayFiles); a folder that is there and cannot be listed fails the copy (FailedListing) |
| `before-<YYYYMMDD>-<n>.smgmp` | a slot or settings call, right before it replaces something | the whole Team File as it was, or the settings files as they were |
| `copy-<YYYYMMDD>-<n>.smgmp` | `mp_keepsafe_make_copy` | the Team Files, and unless `MP_KS_COPY_NO_ACCOUNT` the account |

**Order and numbers.** Copies are ordered by the creation time they record (the manifest's, the copy file's), ties by the number in the name this module gave them, then by name. The number of a new copy is one more than the largest among the names THIS module makes (`<prefix>-<8 digits>-<3 to 9 digits>`, a folder, or `before-`/`copy-` with `.smgmp`) and the stamp's `seq`: a stray name such as `copy-20990101-4294967295.smgmp` counts for nothing and cannot saturate the counter or scramble the "newest 16" (Ordering).

**A copy made right after a cut in the old version's Team File save.** When the version copy holds no `GameData.bin` (the primary is missing) but a `GameData.bin.mptmp` that passes the file's checks, that temporary is the copy's Team File; else a valid `GameData.bin.mpbak`. Nothing is renamed or removed: both files stay as they are in the copy and live (CutSave).

A new copy never reuses or unlinks an existing name: a folder is made with `mkdir` that must succeed, a file with `O_EXCL` after an existence check; on a clash the next number is tried, and with a failed directory listing (the counter is then only the stamp's) a clash simply skips to the next number or the copy fails (CopyFailures "clash", keepsafe_cut_test clash: with the listing failing, every file of every earlier copy is byte-identical afterwards). A failed copy removes only what that call created.

Folder copy: `MANIFEST.ksm` written last: `"SMKM"`, fmt u16 (2; 1 is still read), class 0, seq u32, created s64, version[24], from[24] (the version whose data this is; `none`, `newer`), file count, then per file (path, size, fingerprint), then a CRC-32 of the manifest. The fingerprint is FNV-1a 64 folded to 32 bits (a CRC of a file that ends with its own CRC-32 is one constant per length). Order: the folder, an empty `.unfinished` mark, every file (new, fsynced, read back), ONE whole-device sync, the manifest, a full read-back, the mark removed.

**Pruning** (after every new copy; only ever removes copies, never live data):
- A folder whose manifest cannot be read, or whose files do not all verify, is never deleted and does not count as a copy (PruneAndPins, BlocksAndDamage). A folder marked `.unfinished` goes once a newer verified copy exists.
- Version copies: the 3 newest verified ones stay; the FIRST copy of each version change (from -> to) is pinned and stays. With more than 8 pinned copies, a pinned one beyond the newest 8 goes only when a newer verified copy holds the same files (names, sizes, fingerprints); otherwise it stays. So the number of pinned copies is NOT bounded by 8: 12 updates of unchanged data keep 8 copies, 12 updates that each find other data keep all 12 (PruneAndPins pins-bound; PinnedCount), and a pinned copy whose data no newer copy holds is never removed.
- "Before bringing back" copies: the newest 16 always stay (a file that does not parse is kept and does not count). An older one is deleted, oldest first, only when every Team File slot in it that is not blank is also, in the bytes the game uses, the same slot of this console's file or of a copy that stays (a version copy that stays, a `copy-*` file, another "before" copy that stays); one that holds a slot nothing else holds stays, however old. At 64 such copies a new bring-back that would make another is refused with `MP_KS_TOO_MANY` (asked before the question) and nothing is deleted (BeforeCopies: the 17th replacement keeps the first one's slot 2; 64 unique ones, the 65th is refused, none deleted). Settings in a "before" copy are not slots: such a copy goes beyond the newest 16 (a file of text the player changed by a menu; the 16 stay). `copy-*` files made by the player: never removed.
- A folder is removed in this order: the `.unfinished` mark is written, the manifest removed, then the files, the mark LAST and only when every file is gone (a failed `unlink` leaves the mark and the folder): a cut or a full card leaves a marked folder, never an unmarked half one (keepsafe_cut_test prune: a cut, a torn write and a "disk full" at every call).

## 5. The copy file `.smgmp`

One file, little-endian, at most 1 MiB (real ones are under 100 KB):

```
0   "SMGMPEXP"
8   u16 format version (1)       10  u16 header bytes (64; a later format may make it longer)
12  u32 entry count (<= 64)      16  s64 created (unix seconds, UTC)
24  u32 data hash (StageData CRC of the game data; 0 = unknown)      28  u32 flags (0)
32  char[32] build (game version that wrote it)
64  entries: u16 name length (1..120), u16 0, u32 data length, u32 CRC-32 of the data, name, data
end u32 CRC-32 of every byte before it
```
Entry names (anything else is skipped as "from a newer game"): `mp/saves/GameData.bin` (all six Team Files), `mp/mp.cfg`, `mp/flow.cfg`, `mp/coop.cfg`, `online/online.dat`, `online/online_<8 hex>.dat` (19 characters; AccountNames: Make a Copy, list, inspect and use of one). Never in it: recovery checkpoints, single-player saves, `mp/backups`, conntest / report files, nothing with a path outside these names. A file is listed when its structure and every length and CRC verify (test MakeCopy: every single-byte damage and every truncation is refused). `inspect` and `bring_back_slot` apply the Team File's own checks to its Team File. Make a Copy copies the live Team File when it passes the file's own checks (the checks the game's loader makes), whatever one slot looks like: a file the game loads can be copied (LiveStructure); the slot's structure is checked only when that slot is brought IN (section 6).

**By default a `copy-` file holds the online account token. Treat it like a password.** "Make a Copy to Share" leaves it out. No log line of keepsafe holds a token or an account file's name (test Account searches the log).

`mp_keepsafe_make_copy` takes no path: it writes only under `<data>/mp-backups/`. To move data to another console or card: copy the `copy-*.smgmp` file into `ux0:data/smg/mp-backups/` there; "Bring Back a Copy" lists it. Settings entries in a `copy-` file are never offered (they would be another console's); `console_key` and `upnp_permanent` are this console's secret and router mapping and never come from a copy of another console: a `copy-` file's settings are never offered (MakeCopy writes no settings; Settings: a crafted `copy-` file with settings entries offers none and changes nothing), and mp.cfg brought back from a copy of this console's own kind (a version folder, a `before-` file) - whatever its name says, including a folder or a `before-` file from another console - always gets THIS console's current `console_key` and `upnp_permanent` (the copy's lines are replaced in place, or dropped when this console has none; Identity).

## 6. Bringing an item back

The menus' **Safe Copies** screens (`MpMenuFiles.cpp`) are the caller: **Make a Copy**, **Make a Copy to Share** (`MP_KS_COPY_NO_ACCOUNT`) and **Bring Back a Copy**. They are reached from **How to Play** (**Triangle** on the Multiplayer menu, **OK**, then **Yes** on its second page, `MpMenuMain.cpp`) and with **Triangle** on **Which File?**; **Bring Back a Copy** is also a row where a Team File cannot be read (on **Which File?** and in the list after a crash) and only while at least one copy exists. No run on a console yet.

`mp_keepsafe_inspect` first (read only), then one call per item. The question is the CALLER's (exact words: `share/keep/API.md`); keepsafe asks nothing itself and returns `MP_KS_CONFIRM` when a call that would replace something has `confirmed = 0`.

- **A Team File slot** (`bring_back_slot`): the copy's file for that slot is never blank (blank = never created: `MP_KS_NOTHING`, never replaces anything) and not the same as this console's (NOTHING). This console's slot empty or blank, or no Team File here at all: written without a question (with no Team File here, a new file is made with ONLY that slot: every other slot is blank, the copy's own blank slot when it has one, else all-zero blocks; SlotOnly, cut slot-only). This console's slot in use: `MP_KS_CONFIRM` until confirmed; `inspect` says whether this console's file has progress the copy lacks (`slotLacks`): the copy must have everything this one has, every block (mario, luigi AND the third, config: the same chunks; every galaxy record of this file present with at least the same bits: Power Stars, coin records; every other chunk a bitwise superset), so the same star COUNT with other stars is "lacks" (BringBackSlot, BlocksAndDamage). The slot that comes in must pass the slot-structure check (the game's parsers trust every size), and so must the same slot of the result; this console's other slots are not checked and stay as they are, so a good copy repairs a damaged slot here (LiveStructure: the damaged slot comes back good, the damaged file is in the "before" copy; a damaged slot in the copy is refused with `MP_KS_BAD_FILE` and not offered by `inspect`, which marks it with the blank bit). Before replacing, the current whole Team File is written to a new `before-*.smgmp`, read back and parsed; if that fails (card full, damaged) nothing is replaced (BringBackSlot: no space); with 64 "before" copies that cannot be deleted the call returns `MP_KS_TOO_MANY` first (section 4). Then ONE `mp_save_write_atomic` of the new Team File (the other five slots are this console's current ones); the game's reload hook runs before the call returns (BringBackSlot: the hook sees the new file); the guard (a session, progress in RAM, a save running) refuses with `MP_KS_BUSY` and changes nothing.
- **The online account** (`use_account`): never part of anything else. Without `confirmed`: `MP_KS_CONFIRM`. The account store (`StoreAccount`, which `mp_service.cpp`'s SaveAccount also calls) is the ONLY writer of `online*.dat`: it reads the file the save layer's recovery way, keeps the credential being replaced as `.prev` (older ones move to `.prev.1`, `.prev.2`; each a single atomic write, so a cut leaves a credential in two places, never none) only when this console held it (its own list `online/keepsafe-own.txt`; a console with no list yet: the one there is its own); a foreign credential is never rotated into `.prev`; a newer game's file, or one that cannot be read now, is left alone (`MP_KS_IO`). Everything the store needs is READ before anything is written: a `.prev*` file or the own list that fails to read (anything but "does not exist") makes the store return failure and change nothing, and an own list that fails its own check counts as "no list" (the account being replaced IS kept in `.prev`) (AccountReads). `use_account` returns `MP_KS_BUSY` when the game's guard says so (a session, progress in RAM, a save running) and waits for the save layer's async writer first (AccountGuards); that wait, and the ones in `make_copy` and `bring_back_slot`, are bounded at `MP_SAVE_ASYNC_WAIT_MS` = 15 s, and where the result is checked a writer that does not finish is `MP_KS_BUSY` ("Please wait a moment and try again"; `use_account` does not look at the result of its wait); Make a Copy reads the account files under the account lock, so it never sees the writer's two renames half done (AccountLock). Then ONE atomic write, then `mp_service_shutdown` (Account; keepsafe_cut_test use-account, use-account-back, account-store: a cut at every call, the old credential is always in the live file or in `.prev`, and no foreign credential is ever in `.prev`).
- **Settings** (`bring_back_settings`): only from this console's own copies (a VERSION folder or a BEFORE file); a made copy offers none. One file at a time through its own writer (mp.cfg: `mp_config_replace_held`, the writer's own steps; flow.cfg / coop.cfg: `mp_ui_flow_replace_file`), under the settings lock, taken BEFORE mp.cfg is read or copied (Settings: a spy sees every read of mp.cfg with the lock held), after a `before-*.smgmp` of the current ones; the reload hooks run before the lock is released (Settings; keepsafe_cfg_test: the real settings code and a helper thread saving all the time, under ThreadSanitizer, 50 rounds per run). A newer mp.cfg / flow.cfg / coop.cfg here is left alone; an mp.cfg that does not parse is replaced (ConfigRestore). Both writers `fsync` the temporary file before the rename, as the Team File and account writers do (WritersSync: the order of `fsync` and `rename` of `mp.cfg.tmp` / `flow.cfg.tmp`, in `mp_config_save`, `mp_config_replace_held` and the flow.cfg writer); on a power cut after the rename the file is whole, not zero-length. Both writers keep the previous file as `.bak` and their loaders read the `.bak` when the file is missing; flow.cfg's writer never removes a `.bak` when the file itself is missing (SettingsWriters).
- **Undo** is bringing back the "Before bringing back" copy: the same calls, no special code (BringBackSlot, Settings, cut slot-undo, settings-undo).

## 7. The Vita file system, and what a power cut does

The port does all file I/O through POSIX calls (newlib over `sceIo*`). `rename` onto an existing file fails on the Vita (the code base relies on it), so every replace by the save layer is: write `.mptmp`, fsync, read back, remove `.mpbak`, rename file to `.mpbak`, rename `.mptmp` to file; the settings writers do the same with `.tmp` / `.bak`; `mp_save_recover*` (at start) puts a complete `.mptmp` or `.mpbak` in place. A copy is a new file or folder: written, fsynced and read back one by one, one device sync per folder copy.

**The power-cut model** (`tests/mp/keepsafe_cut_test.cpp`, the third reviewer's `cut` method): every operation runs in a forked child that is killed right before its k-th file-changing call (open for writing, write, rename, unlink, mkdir, rmdir; also fopen for writing, fwrite, fclose of a written stream and remove, which the settings writers use), for every k, once plainly, once with the write torn in half, and (keepfix 5, the reviewer's third mode) once with that call failing with `ENOSPC` while the process goes on and runs the operation to its end. Then the game starts as it does (keepsafe boot, then the save layer's recovery for the Team File and the account, then the settings load), and the test checks: every live file is byte-exact its state before or after the operation (a missing file only where the file's own writer keeps a recoverable copy); no stray file; no verified copy lost except what the uncut operation itself removed (and only behind its unfinished mark); what a completed change replaced is in a verified copy (account: `.prev`); then the game plays on (saves the Team File, mp.cfg, flow.cfg and the account through their own writers), starts twice more (the second as a new version) and every one of those saves is still there; the operation runs again and is not refused; the single-player save folder is byte-identical (bytes, inode, mtime) after every cut. Operations: version copy, prune, make a copy, bring back a slot (in use, empty, no Team File here, only slot N with no Team File here, the undo, 17th "before" copy), use the account (own to foreign, foreign back to own), the account store, settings and their undo, and the failed-listing clash. The numbers of the last run are in the report that came with the commit.

| Step | A power cut leaves |
|---|---|
| a copy, any file | the data untouched; a folder with the `.unfinished` mark (never listed; removed once a newer verified copy exists) or a partial `.smgmp` (never listed; its name is never reused); no stamp change, so the version copy is made again at the next start |
| the stamp write | the old or the new stamp (atomic writer) |
| a slot, after its "before" copy | the old Team File, or the new one with the "before" copy holding the old one |
| a slot, the Team File write | the old file, the new file, or a state `mp_save_recover` repairs at start (the save layer's own tests; the cut test runs it) |
| the account: the `.prev` rotation, then the live file | the old credential live and in `.prev` (maybe twice), or the new one live and the old in `.prev` |
| settings | the old file, the new file, or a missing file with its `.bak` (the loader reads it) |
| a prune | complete copies, or a marked unfinished folder |

Only a real console can prove (nothing of this module has run on a Vita): that `rename` over an existing file fails with an error and not a silent replace (assumed from the code base); that `fsync` of a new file plus ONE `sceIoSync` makes every copied file durable before the manifest is written; that a power cut during `fsync` / `rename` leaves the FAT consistent (the card's file system is not ours; the model cuts at call boundaries and tears whole writes only); the free-space call's numbers; the time `mp_keepsafe_boot` takes after an update; behaviour on a nearly full card; that `opendir` lists a folder completely (prune and the next number decide from listings; a failed listing is tested, a short one is not); whether a quit can overlap a running call (the quit path waits at most 300 ms on `mp_keepsafe_busy`).
